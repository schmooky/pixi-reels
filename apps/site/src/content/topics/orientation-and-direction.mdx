<ConceptPart title="Orientation & direction" lede="One engine, four layouts. How a reel's travel axis works, why start and end are geometric rather than travel-relative, and what stays screen-space.">

A reel can travel down, up, or sideways. Two builder settings control that,
and they do not affect each other:

```ts
new ReelSetBuilder()
  .orientation('horizontal')   // which screen axis the strip travels along
  .direction('reverse')        // which way along it symbols move
```

That gives four combinations on one engine. Anticipation, cascades, the
spotlight, pins, big symbols, pyramids and MultiWays work in all four. The
code is written against the axis instead of against `y`, so nothing is
mirrored or reimplemented for the other layouts.

| | `direction('forward')` | `direction('reverse')` |
|---|---|---|
| `orientation('vertical')` | symbols fall (the default) | symbols rise, a roll-up |
| `orientation('horizontal')` | symbols move right | symbols move left, a sideways banner |

<a id="the-four-concepts-kept-apart"></a>

## The four concepts, kept apart

Many engines fold all of this into the sign of a `deltaY`. Then a horizontal
reel needs a second engine, and the second engine rots. pixi-reels keeps four
things separate so that one engine is enough:

- Orientation: which screen axis the strip runs on. Set for the whole set at
  build time.
- Direction: which way along that axis symbols travel. Per reel.
- Gravity: which way cascade symbols fall. By default it follows the reel's
  direction. `tumble({ gravity })` can pin it to `'forward'` or `'reverse'`
  so a reel spins one way and drops the other.
- Facing: which way is up for the art. Never touched by the other three.

The last one is a rule: travel never changes facing. A reel can spin sideways
and its art stays upright. The engine never rotates a container to fake an
axis, because that would break sprite anchors, flip filters, and render every
third-party symbol on its side. A test asserts zero rotation and unit scale on
every symbol, in all four combinations, at rest, mid-spin and landed.

<a id="main-and-cross"></a>

## Main and cross

Two words cover the whole engine. The main axis is the one the strip travels
along: `y` when vertical, `x` when horizontal. The cross axis is the one the
reels are laid out along, the other one. On a vertical set the reels sit side
by side across `x` and cells scroll down `y`. On a horizontal set it is the
opposite.

`Reel` exposes both for code that must not care which is which: `cellMain`,
`cellCross`, `mainGap`, `crossGap`, `extent` and `mainOffset`.

<a id="what-stays-screen-space"></a>

## What stays screen-space

Your own symbol classes need no changes, because everything a symbol sees is
screen-space, whatever the orientation: `symbolSize(width, height)`,
`symbolGap(x, y)`, `ReelSymbol.resize(width, height)`, `CellBounds`,
`getCellBounds`, `getBlockBounds`, and the position of the `ReelSet` itself.

A horizontal set is the vertical one transposed. Swap width and height and
you have the same board on its side.

```ts
// A 5x3 vertical board.
.symbolSize(120, 100).symbolGap(8, 6)

// The same board, sideways.
.orientation('horizontal').symbolSize(100, 120).symbolGap(6, 8)
```

Indices do not move either. The same `ColumnTarget[]` goes into
`setResult()`, the same shape comes out of `getVisibleGrid()`, and a cell
address means the same cell whichever way the strip runs.

<a id="start-and-end-are-geometric"></a>

## Start and end are geometric

The buffers are named `start` and `end`, not above and below, and not lead
and trail:

```ts
.bufferSymbols({ start: 1, end: 1 })
reelSet.setResult([{ visible: ['A','B','C'], bufferStart: ['COIN'] }]);
```

Start is the smaller screen coordinate: above on a vertical set, left on a
horizontal one. Direction does not change it.

The reason is that a buffer symbol is decoration. It is the coin peeking
above the top row, or a big symbol's tail parked off-window. It means "the
slot just outside this edge". If that were travel-relative, reversing a reel
would teleport every teaser to the other side of the screen. So motion is
directional and buffers are geometric.

The feed edge, the side new symbols arrive from, is travel-relative. You do
not set it. The engine derives it, and you can read it as
`reel.axis.feedEdge` when you need it.

<a id="per-reel-direction"></a>

## Per-reel direction

```ts
.direction('forward')                                        // every reel
.directionPerReel(['forward','reverse','forward','reverse','forward'])
```

Alternating columns, one reversed reel, whatever the design wants.

One rule: a big symbol wider than one reel cannot be combined with mixed
per-reel directions. `build()` throws when the per-reel array holds more than
one distinct value. A uniform array is fine, since the block still travels
one way. The block coordinator assumes every reel a block covers feeds from
the same edge. With mixed directions the block would split mid-spin, so the
builder fails instead. Keep blocks inside one reel, or give the whole set one
direction.

<a id="render-order"></a>

## Render order

Direction does not change which symbol overlaps which:

```ts
.cellStacking('ascending')   // default: the cell at the larger coordinate draws in front
.reelStacking('ascending')   // default: the last reel draws in front
```

The stacking is geometric. Art is lit from above, and flipping the stacking
on a roll-up would make that lighting read backwards. A per-spin reversal
tease would also re-layer the whole board in front of the player. If your art
wants the opposite, pass `'descending'`.

<a id="nudge-is-relative"></a>

## Nudge is relative

```ts
await reelSet.nudge(2, { distance: 1, direction: 'forward', incoming: ['wild'] });
```

Here `'forward'` means the way this reel travels, not down. On a reel built
with `direction('reverse')`, a forward nudge moves upward and feeds from the
right edge. You write no branches.

<a id="composing-two-sets"></a>

## Composing two sets

A banner above a grid is two reel sets in one container. The engine does not
model this, and does not need to.

```ts
const main = new ReelSetBuilder().reels(5).visibleCells(3)./* ... */.build();

const banner = new ReelSetBuilder()
  .orientation('horizontal')
  .reels(1)            // one reel...
  .visibleCells(5)     // ...of five cells, one above each main reel
  ./* ... */.build();

const stage = new PIXI.Container();
banner.y = 0;
main.y = CELL + GAP * 3;
stage.addChild(banner, main);
```

Lay each set out from its own top-left. Scale the container, never the sets
inside it. If you scale one set the other stays behind at the wrong size and
in the wrong place.

The full version, with a banner wild that extends a ways win, is the
[banner-ways](/mechanics/orientation-and-direction/#banner-ways) demo.

<a id="seeing-it"></a>

## Seeing it

You cannot see an axis in a screenshot, so the debug overlay draws it:

```ts
import { debugOverlay } from 'pixi-reels/debug'; // needs pixi-silk, a dev dependency

const overlay = debugOverlay(reelSet, { layers: ['axis', 'feed', 'thresholds', 'hud'] });
```

- `axis`: one arrow per reel, pointing the way it travels
- `feed`: the edge new symbols arrive at
- `thresholds`: the wrap lines; no symbol should ever be drawn past one
- `hud`: a line per reel, such as `r0 VF feed=start spd=... cells=3`

`overlay.describe()` returns the same information as plain JSON, for tests
and for anything that cannot look at a canvas. See [Debugging](/learn/debugging/).
