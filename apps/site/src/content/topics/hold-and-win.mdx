<ConceptPart title="Hold & Win" lede="How a Hold & Win round runs: the state machine, its events, and how to wire the board to your game client.">

Hold & Win, also sold as Lock & Respin or Hold & Spin, is a feature where
coins land, stick, and refill a respin counter until the board fills or the
respins run out. pixi-reels ships it as a built-in board:

```ts
import { HoldAndWinBuilder } from 'pixi-reels';
```

The demos further down show individual tricks. This part shows how the whole
thing fits together and how you drive it from a real game client.

<a id="the-mental-model"></a>

## The mental model

A Hold & Win board is a grid of cells that spin independently. The engine's
unit of spinning is the column, a `ReelSet`. The mechanic's unit is the cell.
So each cell is its own 1x1 reel set, and `HoldAndWinBuilder` wires the grid
and the round choreography around them.

The board is value-blind. A coin is an opaque record:

```ts
{ cell: { reel, cell }, id: 'coin', data: /* anything you want */ }
```

The `id` picks the registered symbol art. The `data` is yours: values,
jackpot tiers, multipliers, collector flags. The board never reads it.
Adders, doublers, collectors and flights to a meter are not board features.
They are game logic you run on top of three openings:

| Opening | What it gives you |
|---|---|
| `board.events` | every beat of the round, with the coin payload |
| `board.symbolAt(cell)` | the live symbol instance, so you can call your own symbol's methods |
| `board.cellCenter(cell)` / `board.cellBounds(cell)` | exact pixel geometry for flights and trails |

Keep that split and any Hold & Win variant is a small amount of game code.
The board never changes.

<a id="the-lifecycle"></a>

## The lifecycle

The board is a three-state machine. `board.phase` reports where it is:
`'idle'`, `'active'` or `'spinning'`.

<Timeline
  beats={['idle', 'active', 'spinning', 'active']}
  edges={[
    { after: 0, label: 'enter(seed)' },
    { after: 1, label: 'respin(hits)' },
    { after: 2, label: 'cells land' },
  ]}
  spans={[{ from: 1, to: 3, label: 'respins left, board not full', loop: true }]}
/>

<Timeline
  beats={['spinning', 'feature:end', 'idle']}
  edges={[{ after: 0, label: 'board fills OR respins hit 0' }]}
/>

1. `enter(seed)` seeds the board with the trigger coins. They lock at once,
   without a spin, and the respin counter arms. The board goes from idle to
   active.
2. `respin(hits)` spins every free cell. The cells named in `hits` land their
   coins. Everything else lands blank. The board goes active, spinning,
   active. If a coin landed this wave the counter resets to full. If nothing
   landed it goes down by one.
3. The feature ends when the board fills or the counter reaches zero, and
   the board returns to idle. Then you collect.

<a id="what-one-respin-fires"></a>

### What one `respin()` fires

Events come in a fixed order. Cells land in stagger order, so the landing
and lock events arrive one by one rather than all at once:

      ],
    },
    { label: 'respins:changed', note: "reason: 'hit-reset' (full) or 'miss' (-1)" },
    { label: 'respin:end' },

  ]}

<a id="wiring-it-to-your-game-client"></a>

## Wiring it to your game client

The board owns the choreography. You own the loop and the result source. A
respin's results come from wherever your real results come from: an RGS, a
mock server, an RNG. The driver is short:

```ts
const board = new HoldAndWinBuilder<{ value: number }>()
  .grid(5, 3)
  .cellSize(72, { gap: 4 })
  .symbols((r) => r.register('coin', CoinSymbol, COIN_OPTS))
  .weights({ coin: 1, empty: 4 })   // how often coins flash past during the spin
  .respins(3)
  .ticker(app.ticker)               // required: drives every cell's reel
  .build();

app.stage.addChild(board.container);

// React to the round however your game presents it: HUD, sounds, flights.
board.events.on('coin:locked', ({ coin, locked, capacity }) => {
  hud.total += coin.data?.value ?? 0;     // you own the value; the board does not
  hud.text = `${locked} / ${capacity}`;
});

// 1. trigger
board.enter(await server.triggerCoins());

// 2. the respin loop: one round per iteration, you pace it
while (true) {
  const round = await server.nextRound(board.freeCells);   // your result source
  const result = await board.respin(round.hits);           // the board animates the wave
  if (result.done) break;                                  // full or out of respins
  // anything between rounds (celebrate, delay, play a teaser) happens here
}

// 3. collect: release the coins and fly them wherever you like
for (const coin of board.lockedCoins) flyToMeter(board.cellCenter(coin.cell), coin.data?.value ?? 0);
board.release(board.lockedCoins.map((c) => c.cell));
```

`respin()` resolves only after the whole wave has landed and the counter has
been updated, so the loop reads top to bottom.

For a [single skip button](/mechanics/hold-and-win/#hold-and-win-skip), call
`board.skip()`. It slams every in-flight cell. The landing, lock and
feature-end flow still resolves. You stop waiting for it. The quicken form,
`board.skip({ mode: 'quicken' })`, lands instead of cutting: every in-flight
cell drops its spin floor, so the wave lands together, and still spins its
symbol in and bounces. Add `speed: 'turbo'` to land it on turbo, or make
quicken the board's default with `skipMode('quicken')` on the builder.

<a id="events-reference"></a>

## Events reference

Every event carries your `TData` on its coins.

| Event | Payload | Fires when |
|---|---|---|
| `feature:enter` | `{ seed, respins }` | `enter()` seeds the board |
| `respin:start` | `{ round, respinsLeft, spinning }` | a wave begins |
| `cell:landed` | `{ cell, coin }` (`coin: null` on a miss) | each cell settles, in stagger order |
| `coin:locked` | `{ coin, locked, capacity }` | a hit cell locks |
| `cells:activated` | `{ cells, capacity }` | `activate()` woke dormant cells; `capacity` is the new full-board count |
| `speed:changed` | `{ name, previous }` | `setSpeed()` moved every cell to another profile |
| `respins:changed` | `{ value, reason }` | the counter changed (`seed`, `hit-reset` or `miss`) |
| `respin:end` | `{ round, hits, respinsLeft }` | the wave finishes |
| `board:full` | `{ coins }` | the last free cell locks |
| `feature:end` | `{ coins, rounds, full }` | the feature is over and the board is idle |
| `coin:released` | `{ coin, remaining }` | `release()` removed a coin (the collect moment) |
| `feature:reset` | `{ clearedCoins }` | `reset()` hard-cleared the board |
| `feature:skip` | `{ inFlight, mode, speed?, payload? }` | `skip()` freed the in-flight cells, placed (`'slam'`) or landing through their stop (`'quicken'`). `speed` and `payload` are the press's options as given |

Two distinctions are deliberate. `release()` means "collect this coin" and
fires `coin:released` per coin, while `reset()` is a hard clear back to idle
and fires a single `feature:reset`, so a HUD that decrements on collect does
not tick on a reset. And `setSymbolAt(cell, id, data)` rewrites a locked coin
in place (a coin becoming MINI, then MAJOR) while keeping the ledger correct.
It throws on a free cell. Placing a new tracked coin is the job of `enter`
and `respin`.

<a id="rectangular-cells-the-lock-animation-dormant-cells"></a>

## Rectangular cells, the lock animation, dormant cells

Three builder options cover what a production board usually needs beyond the
square default:

```ts
const board = new HoldAndWinBuilder()
  .grid(5, 3)
  // art is 202x170: a seam between columns, rows touching
  .cellSize({ width: 101, height: 85 }, { columnGap: 6, rowGap: 0 })
  // 'win' (default) plays playWin() on every lock; 'landing' plays the
  // symbol's playLanding() settle instead; 'none' plays nothing
  .lockAnimation('landing')
  // built, drawn as `sealed`, but outside the feature until activate()
  .inactive(row(0).concat(row(4)), 'sealed')
  ...
```

With `'landing'` or `'none'` the celebration is yours. `await board.playWin()`
pulses every locked coin, or `board.playWin(cells)` a subset, whenever the
game decides, typically on `board:full` or after `feature:end`. A coin that
starts its own landing beat on land (a Spine coin with `autoPlayLanding`, a
sprite that reports its settle through `trackLanding`) keeps it: `'win'`
waits for that beat before the celebration and `'landing'` does not replay
it. The mode can also be a function of the coin that locked, so a collector
celebrates while plain coins only settle:

```ts
.lockAnimation((coin) => coin.id === 'collector' ? 'win' : 'landing')
```

`board.activate(cells)` wakes dormant cells between waves. They show the
empty symbol, join the next respin and count toward `isFull` from then on.
`reset()` seals them again. The rectangular cells, landing-only and growing
clover board demos further down show each of these running.

<a id="draw-order-between-cells"></a>

## Draw order between cells

Every cell is its own reel set, so a coin's `zIndex` only sorts it against its
own buffers. Art the engine lifts above a cell's mask at rest (`unmask: true`)
renders in one layer above all cells, in attach order, which is column-major.
So a lower coin's overflow is covered by the next column's. `cellZIndex`
makes that layer sortable and asks for each cell's order on every place and
landing:

```ts
.cellZIndex(({ cell, symbolId, cols }) =>
  (symbolId === 'grand' ? 1000 : 0) + cell.cell * cols + cell.reel)
```

`board.liftedLayer` is the layer itself, for an effect that has to sit
between the cells and their lifted art. `symbolZIndex(resolver)` is the
per-symbol form from `ReelSetBuilder`, applied inside every cell. See
[big symbols](/mechanics/big-symbols/#zindex-layering).

<a id="speeds-board-wide"></a>

## Speeds, board-wide

Every cell is its own reel set with its own `SpeedManager`. The board
registers speeds into all of them and switches all of them:

```ts
const board = new HoldAndWinBuilder()
  .speeds({ normal: NORMAL, turbo: TURBO, superTurbo: SUPER_TURBO })
  ...
board.setSpeed('turbo');            // every cell, at once; fires speed:changed
board.addSpeed('cinematic', slow);  // one more, after build
```

Cells land in a diagonal wave, and its step is the active profile's
`stopDelay`. The time between reels stopping on a reel set is the time
between wave steps on a board. Each cell spins `(reel + cell) * stopDelay`
ms on top of the profile's `minimumSpinTime`, so NORMAL's 140 ms steps the
wave and TURBO's 0 lands every cell together. `.stagger(fn)` replaces the
shape. It gets the speed's name and profile:

```ts
.stagger((reel, cell, speed, profile) => reel * profile.stopDelay) // column by column
.stagger((reel) => reel * 120)                                     // fixed, whatever the speed
```

The same rule as `reelSet.setSpeed()` applies: a cell already in flight
finishes on the profile it started with, and the next wave runs on the new
one. `board.skip()` is how a turbo press cuts the wave in progress, and
`board.skip({ mode: 'quicken', speed: 'turbo' })` lands it on turbo instead
of cutting it. Each name also gets a `name:tension` variant the board uses
for an anticipating wave.

<a id="own-the-board"></a>

## Own the board

pixi-reels ships boards as two layers:

- `BoardGrid` is the primitive. A grid of cells that each spin
  independently. It knows geometry, instances and spinning, and nothing about
  coins, locks, respins or value.
- `HoldAndWinBoard` is one opinionated board built entirely on the
  primitive's public API. It adds the lock, respin and collect rules.

When the built-in board does not fit, you have three options, in order of
effort:

1. Configure it. Stagger, respins, weights, anticipation and cell chrome are
   all builder options. Most games never go past here.
2. Build on the primitive. If your feature is not lock-and-respin at all
   (pick-and-reveal, cluster-collect, scratch card), skip `HoldAndWinBuilder`
   and use `BoardGrid` directly. The [board grid reveal demo](/mechanics/layers/#board-grid-reveal)
   is a non-Hold & Win board on the primitive.
3. Fork the board. For lock-and-respin with different rules, copy
   `HoldAndWinBoard` and `HoldAndWinState` into your project and repoint their
   imports at `pixi-reels`. Everything they use (`BoardGrid`, `EventEmitter`,
   the `Hw*` types, `cellKey`, `HwEffect`) is public API, so the copy stays on
   supported ground. Then rewrite the reducer. The respin-reset-on-hit rule
   and the board-full-ends-the-feature rule live in `HoldAndWinState`.

The board never reads your `data` and never encodes a paytable. Meaning stays
on your side. The board only moves reels.
